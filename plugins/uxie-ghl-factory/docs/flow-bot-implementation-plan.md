# Implementation plan — Flow-Based Builder

Companion to `flow-bot-probe-spec.md`. The spec says what is unknown; this says what gets built,
in what order, and how each piece is proven.

**Ordering rule:** every offline work item runs before any live one, and the live items are ordered
so the decisive experiment (W3) happens before anything that depends on its answer. No sequencing by
time — only by dependency.

---

## W1 — Reconcile the two catalogues (offline, no account)

**Why first:** the flow-bot surface is described by two files that disagree, and no probe result can
be recorded coherently until they agree on what they each mean.

- `engine/catalog.data.json` — generated by `knowledge/scripts/gen-catalog.mjs`, carries
  `confidence` and an `example:` pointer.
- `catalog/type-cards.json` — generated by `knowledge/scripts/build-type-catalog.mjs` from
  `knowledge/corpus/workflows/30-types/**/*.md`, carries `status` from page frontmatter.

`conv_ai_trigger` is `verified-live` in the first and `source-derived` in the second.

**Do:**
1. Write `knowledge/scripts/check-catalog-agreement.mjs` — for every type present in both, compare
   the confidence/status pair and **print every disagreement by name**, exit non-zero on any.
   Named, never counted: a bare count is how the last two regressions hid.
2. Resolve the flow-bot rows by evidence: `verified-live` requires an example file that **exists**.
3. Wire the checker into `plugin/scripts/` alongside `check-type-catalog.mjs`.

**Proven by:** the checker passing, and its first run's disagreement list recorded in the commit
message — that list is a finding about the whole catalogue, not just this surface.

**Falsified if:** the two files turn out to mean different things by their tiers, in which case the
checker compares the wrong pair and needs a mapping, not an assertion.

## W2 — The 28 dangling example pointers (offline, privacy-gated)

**Do:**
1. Write `knowledge/scripts/scrub-examples.mjs`: read `knowledge/catalog/trigger-examples/*.json`,
   template every identifier — `location_id`, `company_id`, `workflow_id`, `id`, and any
   `conditions[].value` whose field is an id — to `{locationId}`, `{workflowId}`, `{agentId}`.
   **Print every key it templated and every key it left alone**, so a new id-shaped field cannot
   pass silently.
2. Emit into `skills/create-ghl-workflow/catalog/trigger-examples/` so the shipped `example:`
   pointers resolve.
3. Run the repo's existing privacy gate over the output before it is staged.

**Do not:** `cp` the directory. The captures contain a real `location_id`, a real `botId` and real
workflow ids; `knowledge/` has no remote, `plugin/` is public, and this project has leaked client
identifiers four times — once a bare `locationId`.

**Alternative if scrubbing proves lossy:** drop the `example:` pointer from the shipped build rather
than ship a broken one. A missing pointer is honest; a dangling one is a lie the CLI repeats.

**Proven by:** all 94 `example:` pointers resolving from the skill directory, and the privacy gate
passing on a staged diff.

---

## W3 — The binding differential (live, decisive) 🔴

The experiment that decides whether the engine has been shipping unbound flow triggers. Everything
in W4 depends on its answer, so it runs first among the live items.

**Precondition:** Phase 0 + Phase 1 of the spec — a throwaway `FLOW_BUILDER_BOT` built in the GHL
UI, read-only capture taken, and both write gates cleared.

**Do:**
1. Build a flow workflow with our engine on the test account, authored with `convTriggerBotId` (what
   the engine takes today).
2. Read the trigger back **on a separate request**.
3. Record which of the three spec outcomes holds: translated / stored-but-ignored / neither.
4. **Confirm behaviourally** — chat against the throwaway agent and read `get_trigger_logs` for a
   qualified enrolment. A stored shape that never fires is not a binding.

**Then, driven by the result:**

| result | change |
|---|---|
| translated | document the translation in the corpus; no code change; note it on the trigger's card |
| stored-but-ignored | `engine/compiler.mjs:1467` emits a `conditions[]` `botId` entry instead; `edit-driver.mjs:144` likewise; **rewrite** `convai-nodes.test.mjs:139` to pin GHL's form; add a regression test that the old key is *not* emitted |
| neither | escalate before changing anything — the binding is somewhere we have not looked |

**Proven by:** a live read-back showing the binding, plus a trigger log showing the bot actually
fired. Not by a green unit test — a green test is what hid this.

**Falsified if:** the throwaway agent cannot be made to chat on this account, in which case step 4
is unavailable and the result is downgraded to shape-only, and said so explicitly.

## W4 — The mutability differential (live)

Spec Phase 3, rows 1–7, against the throwaway only.

**Do:** one attempt per row, each read back separately, each result recorded with exact status and
body. Row 2 uses whichever binding form W3 proved. No retries.

**Then:**
- Every refusal is added to the trigger's corpus page **and** to its type card, so an author reads
  it before trying rather than hitting a 403 mid-build.
- Row 6's result is checked against the recorded `403 ... type "agent" cannot be deleted`. If it
  now succeeds, that is a loud finding and the recorded 403 in `core/errors.mjs` needs a date-scoped
  caveat.

**Proven by:** a table where every row has a status, a body and a read-back state.

## W5 — The `edit_workflow` guard (code, depends on W4)

`engine/edit.mjs` and `engine/edit-driver.mjs` have zero `workflowType` awareness today.

| W4 showed | what ships |
|---|---|
| GHL refuses the dangerous ops | no guard — record that the engine inherits a server-side guarantee, and cite the refusals. Do not add a guard that duplicates one, it will rot |
| GHL allows any of them | a refusal in the engine: ops touching the entry trigger of a `workflowType:"agent"` workflow throw, with a message naming the orphaning risk. Joins the 147 enforced rules |

**Proven by:** a test per allowed-and-now-guarded op, driven by the live result rather than by
assumption.

## Cross-cutting non-negotiables

- Designated test sub-account only, never a client.
- Both write gates before the first write; every non-GET carries explicit `confirm`.
- A 200 is not proof — read back on a separate request, every time.
- Nothing is deleted, including probe artifacts; they are left named and reported.
- No JWT is printed, echoed or logged; no real identifier crosses from `knowledge/` into `plugin/`.
- Every skipped or templated entry is printed **by name**. A bare `catch {}` once hid two missing
  triggers and an order-dependent regex hid nine types.
- Nothing is pushed without approval.

## What this plan does not cover

- **Building flow bots as a product capability.** This proves and corrects the binding; an authoring
  story for flow bots is separate work.
- **The two unpushed commits** — plugin `117bbce` (token autonomy) and grom `9b76baf` (internal-rail
  removal) — still awaiting a release decision, unaffected by any of the above.
